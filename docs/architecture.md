# Архитектура

## Текущая итерация

main: системные диалоги, проверка файлов и атомарная замена через временный файл в том же каталоге. preload: только create/save/open/importMap. renderer: формы, состояние и PixiJS-поле без доступа к Node.js. shared: схема v4 и миграции v1/v2/v3.

Campaign v4 дополняет метаданные массивом maps и отдельным view={activeMapId,cameras}. Map содержит UUID, название, width/height исходного изображения и data URL (только PNG/JPEG base64). Камера хранит x/y в пикселях поля и zoom; размер изображения не меняется. У каждой карты своя камера. Встроенные изображения обеспечивают переносимость одного JSON без ссылок на исходные файлы. Это промежуточный формат до внедрения SQLite/ZIP, а не готовый формат пакетов правил.

Импорт проверяет объём, сигнатуру PNG/JPEG, декодирование nativeImage, размеры. Открытие и сохранение также декодируют изображения и сравнивают размеры. До 20 карт, 15 МБ импортируемого изображения, до 8192 по стороне и 32 млн пикселей; партия до 100 МБ. При невалидном файле текущая партия не заменяется. v1 мигрирует в память без изменения исходного файла; сохранение пишет v4.

PixiJS управляет отдельным canvas. Зум сохраняет точку под курсором; кнопка вписывания центрирует изображение. ResizeObserver обновляет размер рендера, камера сохраняется. Ресурсы canvas/текстуры освобождаются при переключении. Официальный модуль pixi.js/unsafe-eval заменяет динамическую генерацию функций интерпретатором для строгой CSP; разрешение unsafe-eval в CSP **не добавлено**. Предусмотрено сообщение об ошибке рендера. Графическая производительность на Windows ещё не измерялась.

Сохранение ручное; создание, импорт и изменения камеры помечают партию несохранённой. При закрытии или замене есть предупреждение. Автосохранения и резервных копий пока нет.

## Реализация сетки (итерация 3)

Каждая Map содержит grid={cellSizePx,originPx:{x,y},visible}. Координаты — пиксели исходного изображения. Новая/старая карта без сетки получает размер 64, начало (0,0), visible=false. Отдельный view.cameras не меняет калибровку. v1/v2 преобразуются в память без записи исходного файла; сохранение пишет v4.

Геометрия в domain/grid.ts не зависит от React/Electron/PixiJS: преобразования screen↔image, image→cell через floor, cell→origin. Отрицательные номера клеток допустимы до начала сетки. Линии повторяются в обе стороны от origin, ограничены пересечением изображения и viewport. Pixi Graphics рисует их после карты толщиной 1 экранный пиксель. Геометрия пересчитывается при калибровке, камере и размере viewport, без повторной загрузки изображения. Если cellSizePx*zoom<6, линии временно не рисуются и UI объясняет причину; параметры не меняются.

Поля чисел применяются кнопкой после проверки диапазонов: 4–4096 для размера, ±8192 для origin. Дробные значения поддерживаются. Флаг видимости применяется сразу. Несохранённые изменения отмечаются как обычно. Изменение размера или origin не меняет камеры.

## Инструменты сетки (итерация 4)

Пользователь изменил содержание итерации 4: инструменты калибровки вместо персонажей. Подтверждено: разные метры на клетку для разных локаций. Grid дополнен metersPerCell (0.1–1000) и locationKind (custom/house/forest). Старые v1–v3 мигрируют без записи исходного файла, grid получает 1 м/клетку и custom как явно обозначенное исходное предложение. Сохранение пишет v4.

Режим перемещения сетки хранится только в UI. Смещение origin += screenDelta/zoom с ограничением ±8192; камера и размер клетки не меняются. Координатные поля синхронизируются с применённым grid. Переключение карты сбрасывает инструменты.

Пресеты — локальный детерминированный помощник с ручным выбором типа, без распознавания, сервера и моделей. Предложения: дом — 12 клеток вдоль короткой стороны и 1 м/клетку; лес — 40 и 5. Значения редактируемы и не считаются утверждёнными правилами R Prison. Размер клетки clamp(min(width,height)/count,4,4096). Выбор пресета сам по себе не меняет данные до нажатия кнопки.

Точная калибровка: два щелчка переводятся screen→image, длина в пикселях делится на (расстояние в метрах / metersPerCell). Первая точка задаёт origin, оси не поворачиваются. Разрешены только точки внутри карты; нулевой отрезок, неположительная длина и выход размера за пределы отклоняются. Точки визуально отмечены поверх canvas и не попадают в файл. Режимы калибровки и перемещения сетки взаимно исключаются.

Метры не меняют расход ОД автоматически. При разных метрах/клетку правило «1 клетка = 1 ОД» не обеспечивает одинаковую физическую скорость. Согласование пересчёта скорости/стоимости движения остаётся до итерации движения. Не зашивать в UI «лес замедляет».

## Целевая модель (предложение)

Campaign: снимок Ruleset, сцены, персонажи. Scene: Map, токены, геометрия, зоны. Map: изображение и Grid. Token: Character, клетка и занимаемая область. StatBlock: исходные характеристики и текущие ресурсы; производные значения вычисляются. ItemTemplate и ItemInstance разделены. EffectDefinition задаёт механику, Effect — активный экземпляр. Encounter хранит участников, инициативу, порядок и раунд. Ruleset версионирует характеристики, ресурсы, формулы и действия.

Команды проходят прикладной слой, независимое ядро выдаёт результат, события и объяснение. Состояние и журнал сохраняются транзакцией. Отмена возвращает исходное состояние, результаты бросков сохраняются. Генератор случайных чисел подменяемый.
Сетка: cellSizePx и originPx в координатах исходного изображения. image=(screen-cameraOffset)/zoom; cell=floor((image-origin)/cellSize). Камера хранится отдельно. Стены — отрезки в координатах изображения. Для крупных текстур понадобится уменьшенная копия или разбиение.

Редактор формул использует ограниченное дерево выражений, проверяет ссылки, типы, циклы и сложность. Модификаторы: исходные изменения → производные формулы → модификаторы результата → ограничения. Сложение/замена эффектов и триггеры задаются явно; цепочки ограничены.

Предлагаемое полное хранение: SQLite с миграциями, assets по хешу, штатные backup, переносимый ZIP. До миграции резервная копия; импорт ограничивает размеры и пути, проверяет ссылки и совместимость. Изменение каталога не обновляет партии молча.

Папки будущих модулей: application/, domain/{model,rules,movement,combat}, infrastructure/{storage,assets,migrations}; renderer/{panels,editors,board}. PixiJS подключён во второй итерации.

## Персонажи и токены (итерация 5)

Campaign v5 хранит characters[] и tokens[] отдельно от maps и view. Character: UUID, имя, kind=character/npc, footprint={width,height} (целые 1–10), nullable portrait (PNG data URL до 2 МБ). Token: UUID, mapId, characterId, column/row. Размер берётся из персонажа, а положение принадлежит токену. Допускаются несколько токенов одного персонажа и разные карты. Отдельная Scene пока не нужна: на этой итерации карта является единственным полем размещения.

v1–v4 открываются без изменения исходного файла с пустыми массивами characters/tokens, сохранение пишет v5. Zod проверяет уникальность UUID, ссылки, весь footprint внутри изображения и отсутствие пересечения токенов одной карты. Математика footprintFits/footprintsOverlap в domain/tokens.ts независима от UI. Касание границ занятых областей допустимо. Частичные клетки у краёв не принимаются. Камера не влияет на игровые координаты.

Токены — доступные HTML-кнопки поверх PixiJS canvas с тем же преобразованием image→screen. Перетаскивание имеет временный preview без изменения данных до отпускания, затем выбирается ближайшее начало клетки. Отказ оставляет прежнее положение. Круглый портрет вписан в минимальную сторону footprint, выбранная прямоугольная область обведена пунктиром. DOM-слой позволяет клавиатурное управление; производительность 30 токенов/60 FPS ещё не измерена. Замена слоя рендера не требует менять модель и геометрию.

Режимы калибровки/сдвига сетки/размещения персонажа отключают взаимодействие с токенами, переключаются взаимно. Токен останавливает всплытие pointer-событий, чтобы не двигать камеру. Координаты хранятся клетками и следуют новой калибровке; изменение grid проверяется со всеми токенами и отклоняется при выходе за карту.

IPC importPortrait не принимает произвольные пути: использует системный диалог, проверяет сигнатуру, декодирование, размеры, уменьшает до 512px и возвращает PNG data URL. Открытие/сохранение дополнительно декодирует портреты. Портреты сохраняются в каталоге один раз на персонажа, а не на каждый токен. Удаление персонажа каскадно удаляет токены после подтверждения; удаление токена не меняет каталог. Редактирование персонажа и undo ещё не реализованы.

## Редактор разметки (итерация 6)

Map.annotations[] в формате v6 (до 500 объектов, уникальные UUID внутри карты). Дискриминированное объединение Annotation:
- wall: from/to в пикселях исходного изображения, destructible, hp (1–100000; используется только для разрушаемой стены);
- cover: from/to противоположных углов прямоугольника, level=light/medium/nearFull;
- elevation: прямоугольник и heightMeters относительно условного нуля карты (−1000…1000);
- liquid: прямоугольник и liquidType=water/oil/acid/lava/other;
- light: center и radius в пикселях.
Все содержат id/name/visible. Zod проверяет конечные координаты, границы карты, минимальную длину/стороны 1px и отсутствие дубликатов. Свет может выступать за границы карты: визуально обрезается. Миграция v1–v5 добавляет пустые annotations без изменения исходного файла и сохраняет каталог/токены/камеры.

SVG-слой между PixiJS и DOM-токенами использует translate(camera.x,camera.y) scale(camera.zoom), clipPath по изображению и линии постоянной экранной толщины. Свет — простая прозрачная область, без стен/видимости. Сетка и разметка независимы: перекалибровка не меняет пиксельные координаты annotations. Рендер производительности ещё не измерен.

Инструменты разметки взаимно исключают размещение токена, калибровку и сдвиг сетки. Два щелчка создают черновые точки только в UI, данные меняются после кнопки применения. Третий щелчок начинает выбор заново. Выбор — по списку или pointer-событию SVG. Можно заменить геометрию двумя точками, изменить свойства, скрыть и удалить. Прямое перетаскивание и undo не реализованы. Поле visible означает видимость разметки мастеру, а не активность будущих игровых эффектов.

Блокировка пути, расчёт укрытия, урона стенам, эффекты жидкостей и высот не реализованы. Сохранённые свойства — подготовка данных для будущего игрового ядра, а не зашитые правила боя.

## Навигация после итерации 6

По запросу пользователя стартовый экран содержит только создание/открытие партии. Наличие campaign переключает App на рабочий экран с общей панелью и вкладками maps/characters. tab — локальное состояние UI и не записывается в JSON. Создание/открытие выбирает maps и очищает режим размещения. Characters и карта не размонтируются при переключении вкладок (hidden), поэтому ввод и инструменты не теряются, PixiJS обновляет viewport через ResizeObserver. Кнопка размещения из каталога активирует maps автоматически.

Возврат к выбору партии вызывает имеющуюся проверку несохранённых изменений, после подтверждения очищает campaign/dirty/placement/name. Прямое открытие другого файла сохраняет текущий campaign при отмене или ошибке. Вкладки имеют ARIA tablist/tab/tabpanel и управление стрелками. Формат v6 неизменен. Это уточнение интерфейса до следующего этапа редактора правил.

## Правила и вычисления (итерация 7)

Campaign v7 содержит собственный Ruleset {id,name,revision,engineVersion:1,stats[]}. StatDefinition — base {key,name,defaultValue} или derived {key,name,formula}. Character.values хранит исходные числовые значения по ключам; производные значения не сохраняются. Миграции v1–v6 добавляют пустой снимок правил и values={} без изменения исходного файла. Первая запись сохраняет v7. Старый файл без снимка получает новый UUID при открытии; после сохранения UUID стабилен.

Игровое ядро domain/rules не зависит от UI/Electron. Рекурсивный спуск разбирает строку в AST с белым списком операций/функций. Нет eval, Function, обхода свойств, вызовов пользовательского кода или импорта модулей. Ограничения: 64 показателя, 512 символов/256 токенов/128 AST-узлов, 32 уровня синтаксической вложенности; значения входа ±1e9, результата ±1e12. Ключи регулярные, опасные/зарезервированные имена отклоняются. Значения вычисляются через Map; проверяются ссылки, дубли и циклы зависимостей.

При вычислении зависимости кешируются, результат содержит трассу: имя/ключ, формулу, использованные значения и итог. if/логические операции ленивые внутри выражения. Весь список показателей проверяется/вычисляется; ошибка любого отдельного вычисляемого показателя показывает ошибку расчёта. Деление на ноль может зависеть от входных значений, поэтому это runtime-ошибка, а не повод отклонять корректный синтаксис снимка. Случайных бросков пока нет.

Вкладка «Правила»: черновик, применение только после проверки, пробный калькулятор и источник значений персонажа. Применение увеличивает revision, прежний снимок заменяется явно, без истории. Неприменённый черновик/пробные значения не сохраняются. Вкладка «Персонажи» также позволяет редактировать исходные значения и видеть расчёт. Изменение ключа оставляет прежние значения неиспользованными, предотвращая молчаливую потерю; максимум 256 ключей на персонажа.

Слой пока покрывает показатели, формулы и условия. Отдельные ресурсы/HP, модификаторы, правила сложения эффектов, броски и действия будут добавляться следующими итерациями. Нет автоматического назначения R Prison, общего каталога правил или отдельного импортера пакетов.

## Готовые правила после итерации 7

По прямому запросу пользователя createCampaign теперь выбирает конфигурацию rPrisonDraft() вместо пустого набора. Старые партии сохраняют свои снимки; явная кнопка применения готового набора заменяет определения с подтверждением, сохраняет UUID партии/правил и увеличивает revision. Миграции по-прежнему создают пустой набор для файлов без правил. Формат v7 неизменен.

Формулы/имена/defaults R Prison хранятся в domain/presets/rprison.ts, не в UI. Генерируется отдельный снимок на каждую партию. Указаны исходные характеристики, уровень, броня, HP/ОД-максимумы и бонусы урона. Создание персонажа показывает поля применённых base-показателей; карточки всегда показывают evaluateStats без раскрытия редактора. Все игровые значения выводятся из definitions, без фиксированных имён характеристик в Characters.

Справочные FormulaExample также определены в конфигурации; общий UI использует безопасный движок и ручные значения. Они не связаны с ресурсами/боевыми командами и не входят в снимок партии: это явно обозначенные калькуляторы версии v1.1, а не активные правила текущего боя. Автоматические броски, действие брони как поглощения, реакции и расход ресурсов остаются будущими этапами.

## Каталог и снаряжение (итерация 8а)

Этап 8 разделён на 8а (предметы) и 8б (способности/перенос), чтобы отдельно проверить сохранность экземпляров. Campaign v8 содержит itemTemplates[] (до 200) и items[] (до 1000). Миграции v1–v7 добавляют пустые массивы, сохраняя правила/карты/каталог персонажей. Формат не совместим со старым приложением.

ItemTemplate: UUID, revision, name/category/description, nullable damageDice, maxDurability/maxCharges. Кости — только ограниченные данные 1–99d2–1000 с необязательным целым модификатором. ItemInstance: UUID, ownerId|null, template (полный снимок), durability/charges, equipped. createItem копирует шаблон, каждая выдача получает новый UUID. Изменение и удаление живого шаблона не меняют снимки старых экземпляров. Из-за самодостаточного снимка ссылка на живой шаблон не обязательна.

Владелец должен существовать в партии либо быть null (общий запас). Ресурсы целые 0…максимум снимка. В общем запасе equipped запрещён. transferItem меняет владельца и сбрасывает equipped. При удалении персонажа все его вещи освобождаются в запас, а не удаляются. UUID шаблонов/экземпляров уникальны в соответствующих массивах. Все проверки применяются и к загруженным JSON.

Вкладка «Предметы»: создание/редактирование версий шаблонов, выдача, фильтр инвентаря, передача, изменение состояния и отметка экипировки. Карточки персонажей показывают их вещи. Экипировка сейчас — только ручная отметка, без влияния на расчёты. Автоматические атаки, модификаторы снаряжения, способности и перенос партий не входят в 8а.

## Фотографии, распределение и импорт (пользовательское обновление 8б)

ItemTemplate.image — nullable PNG data URL по общей схеме images.ts (до 2 МБ); снимки экземпляров копируют поле. Старые v8 мигрируют в v9 с image=null, не теряя инвентаря. Фото через ограниченный IPC/диалог нормализуется до PNG/512px, при открытии/сохранении также декодируется. Редактирование фото шаблона не меняет существующие снимки. Повторяющиеся фото в инвентаре декодируются при валидации один раз через Set; сохраняются внутри снимков, общий лимит партии прежний.

Inventory — отдельная вкладка. Выбранный UUID владельца, источник и поисковая строка хранятся только в UI. HTML drag-and-drop передаёт MIME application/x-rprison-item с {kind:template|instance,id}. Payload проверяется, объект ищется в текущей партии, владелец проверяется. Шаблон создаёт новый UUID и снимок; существующая вещь передаётся без клонирования ресурса и снимает equipped. Падение на свой же инвентарь — без изменений. Поиск регистронезависимый по имени/описанию. Кнопка даёт тот же сценарий без drag-and-drop.

ContentPack: {format:rprison-content,version:1,characters:[данные Character без UUID],items:[ItemTemplate без UUID/revision]}. Внешние идентификаторы не принимаются. native IPC import-content выбирает файл, ограничивает его 10 МБ, парсит JSON, проверяет схемы/изображения. Ошибки возвращают поля проблемного JSON. Renderer показывает предварительный список; mergeContent проверяет ключи values относительно base-показателей партии и лимиты, выдаёт новые UUID и добавляет весь пакет одной операцией. Повторный импорт намеренно создаёт копии, не обновляет по имени. Сравнение ключей не является доказательством семантической совместимости разных систем.

Объекты/фото импортируются как данные, не исполняются. Локальные пути/URL/SVG в image/portrait не разрешены. Поставляемый examples/content-template.json проходит ту же схему. Это импорт каталога персонажей/шаблонов, а не перенос сцен, вещей владельца, токенов, способностей или правил между партиями. Последние остаются следующей задачей.

## Способности и перенос (итерация 8в)

Campaign v10: abilityTemplates[] (до 200) и abilities[] (до 1000). Ability {id,revision,name,description,costText,maxUses}. AssignedAbility {id,ownerId,definition,usesRemaining} хранит снимок; оставшиеся использования не превышают maxUses. maxUses=0 — отсутствие лимита, счётчик хранится 0. Владелец должен существовать, идентификаторы уникальны. Старые v1–v9 получают пустые массивы без изменения остального. Стоимость/описание не исполняются; счётчики изменяются только вручную, без триггеров хода/сцены и расхода ресурсов.

CharacterBundle {format:rprison-character,version:1,rules,character,items,abilities}. Схема проверяет принадлежность всех предметов/способностей персонажу и уникальность. Фото встроены. Экспорт не включает карту, токены, общий запас или чужую собственность. Отдельный ограниченный IPC принимает только пакет, использует системные диалоги, проверяет схемы/изображения и размер 20 МБ. writeJsonAtomic общий для партий/пакетов, временный файл в том же каталоге с fsync и rename; при превышении лимита старый файл сохраняется.

Домен transfer сравнивает engineVersion и отсортированные определения показателей: ключи/типы/умолчания/AST формул; имена, UUID и ревизии не участвуют. AST игнорирует пробелы/лишние скобки, но не выполняет алгебраическую нормализацию. Строгое несовпадение блокирует импорт. Целевая партия не получает новые правила. Новые UUID выделяются персонажу, экземплярам и назначениям/снимкам; ресурсы/фото/экипировка/оставшиеся использования сохраняются. Источник не удаляется. Копия добавляется одной валидацией или не добавляется вовсе, без автоматического размещения токенов и добавления шаблонов в библиотеку цели.

Перед добавлением UI показывает имя, количества и ошибку совместимости; черновик переносимого пакета остаётся локальным для текущей партии. Полноценная семантика способностей/модификаторов будет добавлена позже; сравнение правил сейчас ограничено вычислительным слоем показателей.

## Движение (итерация 9)

Подтверждено пользователем: 1 ОД/м, диагональ ×√2. Ruleset.movement={budgetStat,mode,diagonal}; R Prison использует ap_max/meters/true. Другие правила могут выбрать источник в редакторе. Character.resources — отдельный словарь текущих остатков (0…1e6, до 64 ключей), не исходные values. Отсутствующий остаток означает полный вычисленный максимум; сохранённый ограничивается максимумом при чтении. Движение всех токенов одного персонажа расходует общий ресурс. Перенос сравнивает movement вместе с формулами и сохраняет resources.

Campaign v11 мигрирует v1–v10 с resources={}, movement по умолчанию. Для старого набора с известной формулой ap_max определяется источник R Prison; остальные наборы требуют выбора. Исходный файл не меняется до сохранения.

Домен movement: Dijkstra с минимальной кучей и ограничением 20000 позиций. Стоимость ребра — metersPerCell * (1 или √2), либо 1 для поддерживаемого data-режима cells. Конец, соседние ортогональные позиции диагонали и размер footprint проверяются относительно границ/токенов. Swept footprint — выпуклая оболочка двух прямоугольников; отрезок стены проверяется на пересечение открытой внутренней области оболочки после быстрого AABB-фильтра. Касание границы разрешено. visible не выключает физическую стену, destructible не означает разрушенную стену. Остальная разметка пока не участвует.

Движение повторно рассчитывает путь из актуального состояния, атомарно обновляет токен и ресурс и возвращает стоимость/путь. Отказ не изменяет данные. Результат ограниченного поиска явно помечается partial; не найденные клетки при этом не считаются доказанно недостижимыми. Сравнения стоимости имеют допуск 1e-9; отображение округлено, ресурс хранит полную числовую точность.

Board хранит выбор/предпросмотр, показывает один SVG path доступных клеток и маршрут центров footprint. Заливка мемоизирована; поиск не выполняется при скрытой вкладке или расстановке. Перетаскивание и щелчок используют одинаковую доменную команду. Alt-перетаскивание пустого места панорамирует, снятие выбора возвращает обычную камеру. Отдельный режим мастера выполняет прежнюю расстановку без пути/ОД, сохраняя проверку конечной позиции.

Undo хранит один снимок до последнего движения в памяти App. Любая последующая игровая правка сбрасывает его; камера не сбрасывает, при восстановлении сохраняется текущий view. Открытие/выход из партии очищают undo и режим мастера. Ресурс восстанавливается вручную; автоматические ходы, урон стенам, стоимость зон и боевые действия ещё не реализованы.

## Разделение подготовки и игры (итерация 10)

Campaign v12 добавляет session={started,tacticalMovement}; v1–v11 получают false/false без изменения исходных файлов, персонажей, ресурсов и остальных данных. domain/session.ts начинает игру при наличии поля и включает расход движения только после начала. Начало игры выбирает первое поле, если активного нет. Не создаёт копий персонажей/предметов и не сбрасывает ресурсы. Encounter и очередь ходов пока отсутствуют.

Экран configure/play — локальное UI-состояние. Новая/мигрированная партия открывается в configure; started=true — в play. Переход в конфигуратор не завершает игру, возврат не запускает её заново. Оба экрана работают с одной Campaign; поля подготовки и текущие позиции/владельцы/счётчики сохраняются совместно. Редакторы правил, каталога/создания персонажей, геометрии и сетки доступны в configure, выдача и изменение экземпляров — также в play. Переключение сбрасывает только временные инструменты и историю отмены, не данные.

В подготовке перемещение — расстановка без стоимости/пути. В play свободное движение использует тот же поиск пути и ограничения геометрии, не обращается к показателю бюджета и не изменяет resources. TacticalMovement=true включает существующую стоимость и бюджет. В обоих режимах поиска действует предел 20000 позиций. Тактическое движение — не модель боя; переключатель не восстанавливает ОД. Импорт/экспорт персонажа не переносит session.

## Предметы на поле (итерация 11а)

Campaign v13: ItemInstance содержит ground=null | {mapId,column,row}. На поле экземпляр не имеет ownerId и equipped=false; в инвентаре/запасе ground=null. Это одна вещь с неизменными UUID/снимком/изображением/ресурсами, без дублирующего списка размещений. Проверка всей партии гарантирует существование карты и целую клетку с footprint 1×1 в пределах изображения. v1–v12 получают ground=null, session и ресурсы не сбрасываются.

Команды domain/ground-items.ts проверяют поля/владельца и атомарно возвращают новую Campaign; transferItem всегда очищает ground. В Inventory предметы на поле исключены из запаса/списков выдачи; общий список Items показывает поле и позволяет передать вещь. Экспорт персонажа включает только принадлежащие ему вещи. Перенос с поля — действие мастера без стоимости/дистанции, допускается совпадение с другими вещами/токенами; поиск пути не учитывает предметы.

GroundItems даёт поиск и размещение/передачу, GroundMarkers рисует HTML-маркеры с фото в координатах камеры над Pixi и токенами; drag/стрелки и список позволяют менять положение. Размещение предмета взаимно исключает размещение персонажа и инструменты карты. При смене карты/режима/вкладки временный инструмент сбрасывается, размещение остаётся в модели. Калибровка сетки сохраняет клеточные координаты, валидация отвергает выход за границы.

## Карточка и очередь боя (итерация 11б)

Campaign v14 добавляет encounter=null | {id,participants:[{characterId,initiative}],round,turnIndex,recovery,apStat,previousTacticalMovement}. Проверяются уникальность участников, существование персонажей, корректный индекс/раунд; активный бой требует started/tacticalMovement=true и совпадение apStat с правилом движения. Персонаж — один участник независимо от количества токенов и карт. Бой общий для партии, не привязан к одному полю.

Ruleset.healthStat связывает текущие HP с ключом максимума; R Prison задаёт hp_max, старые правила без поля распознают этот ключ при наличии, если он не занят бюджетом движения. Явный null не переопределяется. HP и ОД не могут ссылаться на один показатель. Перенос персонажа проверяет и healthStat; старые пакеты нормализуются тем же rulesetSchema.

resources.ts рассчитывает максимум через evaluateStats, ограничивает ресурс диапазоном 0..1000000, отсутствие остатка означает максимум, эффективный остаток min(maximum,stored). setResource записывает только выбранный ресурс; ручное восстановление записывает максимум, не удаляет запись. Максимумы и базовые значения не меняются. CharacterCard — модельная боковая карточка без модального окна: выбор хранится в UI, отображение общих ресурсов/инвентаря/назначений, редактирование через команду.

encounter.ts: startEncounter проверяет участников/бюджет, сортирует стабильно или оставляет ввод, включает тактическое движение и входит в первый ход. nextTurn увеличивает индекс/раунд. Вход в ход восстанавливает только входящего при turn; при round — всех только на границе раунда (включая старт); manual — никого. Команды атомарны, React-эффекты не вызывают восстановление. reorder сохраняет текущего участника и ресурсы, без скрытого входа в ход. endEncounter сохраняет ресурсы/позиции и возвращает предыдущее тактическое состояние. Все переходы очищают историю отмены движения через commit.

moveWithPath проверяет текущего участника и принудительно списывает ОД в бою, даже если вызывающий передал spend=false. Расстановка мастера и конфигуратор используют отдельный путь размещения без этих ограничений. Карточка разрешает ручные исправления ресурсов любого персонажа; HP=0 не пропускает ход автоматически. Удаление участника/смена источника бюджета блокируются схемой; удалить токен можно без удаления участника. Открытие/смена режимов/полей и перестановка не восстанавливают ресурсы повторно. История боя, атаки, броски, эффекты и автоматическое пополнение способностей остаются вне этой итерации.
